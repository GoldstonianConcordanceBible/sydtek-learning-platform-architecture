# RELATIONSHIP TO CASE STUDIES

Case studies should receive stable IDs.

Recommended format:

`CASE-[PROGRAM]-[NUMBER]`

Examples:

- `CASE-MKT-001`
- `CASE-AI-001`
- `CASE-GRT-001`
- `CASE-SCM-001`
- `CASE-W4-001`

Case studies should preserve:

**WHAT HAPPENED  
→ WHAT WAS BELIEVED  
→ WHAT WAS DONE  
→ WHAT HAPPENED NEXT  
→ EVIDENCE  
→ LESSON**

Do not rewrite historical cases solely to make outcomes appear successful.

---

# RELATIONSHIP TO CREDENTIALS

Credentials should resolve to:

**COURSES  
→ COMPETENCIES  
→ ASSESSMENTS  
→ ARTIFACTS  
→ COMPLETION RECORD**

Long-term objective:

A credential should communicate not only that a learner completed content, but what capability was demonstrated.

---

# RELATIONSHIP TO PUBLIC CLAIMS

All public institutional claims must be classified.

Examples:

- internally documented
- externally verified
- partner corroborated
- formally accredited
- credit recommended
- institutionally accepted
- proposed
- experimental

Do not collapse these categories.

Examples:

**“Accreditation-ready”** is not the same as **“accredited.”**

**“Credit recommendation”** is not the same as **“credit awarded.”**

**“University partnership”** is not the same as **“degree-granting authority.”**

---

# VERSION CONTROL

This repository follows semantic versioning principles at the architecture level.

## Major version
Structural institutional change.

Example:

`v1.0 → v2.0`

## Minor version
Additive architectural capability.

Example:

`v1.0 → v1.1`

## Patch-level correction
Non-structural clarification, typo, or correction.

Example:

`v1.1.0 → v1.1.1`

Major institutional rules must not be silently overwritten.

# CANONICAL HIERARCHY

If two documents conflict, interpret the hierarchy as:

1. Applicable law / binding agreement
2. Formal institutional governance
3. Canonical architecture
4. Program standard
5. Course standard
6. Course implementation
7. Delivery-platform implementation

The delivery rail does not override canonical academic architecture.
